ModelClaim

高密度多模型 GPU 池化控制面 · 给引擎进程做一个 lightweight 的 model-kubelet

把 GPU 池化,在模型粒度上高密度装箱——N 个模型共享一张卡的 HBM 与算力。phase-1 首 PR 聚焦跑通核心机制:声明式 apply、load-only 放置、kvcached engine、readiness gate、路由、删除 stop。底座是上游 kvcached(弹性 KV)+ vLLM sleep(launch flags 保留);高级策略层移入 phase-2。

真机验证 · Lambda A10 / minikube full-k8s 首 PR · phase-1 trim · 5 commits feat/kvcached-sleep-integration 基线 1 claim : 1 replica
§1·2

背景与目标为什么要池化,做什么 / 不做什么

推理成本由长尾模型主导:大量低频/中频模型各自独占 GPU(1 model : 1 GPU),利用率极低;静态切分(MIG、按比例分卡)不随负载漂移。取 ServerlessLLM 的"分层加载 + 局部性 + scale-to-zero"路线,舍弃 Aegaeon 的 token 级调度。大 HBM 机型(B300)一等公民:权重常驻为主,驱逐是安全阀。

目标

  • 模型粒度 N:1 共卡:每模型独立引擎进程,弹性共享 KV(kvcached)
  • 声明式:kubectl apply 一个 ModelClaim 即完成放置/激活/路由,无每模型 Deployment
  • phase-1 核心机制:load-only 放置 → activate → readiness gate → route → delete stop
  • 生产可观测:控制面 lifecycle 指标 + runtime KV 观测指标

非目标

  • 不做 token 级调度(Aegaeon 路线)
  • 不做在线迁移(低 ROI)
  • 不 fork kvcached(只作机制层,经 kvctl / /dev/shm 驱动)
  • 首版不做多副本负载伸缩(replicas 字段已留)
  • 首 PR 不含 KV 配额/回收、sleep driver、scale-to-zero、request hold、节点 locality writer

原子能力层上游依赖 —— 两个正交的机制

kvcached · 弹性 KV

CUDA VMM 按需映射物理页。每引擎独立 KVCACHED_IPC_NAME;phase-1 只读 /dev/shm MemInfoStruct(3×int64:total/used/prealloc)做观测。

kvctl 配额执行器和策略层移入 phase-2。

vLLM sleep · 权重卸载

--enable-sleep-mode + VLLM_SERVER_DEV_MODE=1 作为 launch flags 保留,phase-1 不驱动 /sleep//wake_up。

sleep driver 与 kvcached 正交,移入 phase-2。

测试指南验证上游原子机制;首 PR 只使用 kvcached launch、KV 观测和 sleep launch flags。

§5

核心机制把"能跑起来"升级成"设计得住" —— 机制 · 关键决策 · 失效收敛

心智模型 = 给引擎进程做一个 lightweight 的 model-kubelet。k8s 管 pod;pod 内 N 个引擎进程的生命周期 / 探活 / 摘流由我们的 agent 自己管。优先级:先把 5.1 / 5.2 / 5.5 / 5.6 的静态系统层做扎实,5.3 / 5.4 动态能力降级。

5.1运行时封装 + 声明式对账

常驻三层:controller(决策)→ agent(常驻 in-pod 监督器,pod 入口即它)→ engine procs。把"人肉 bash 进容器手敲 launch"固化成常驻角色。

协议从命令式 RPC 升级为期望态对账:agent 上报的 {phase,ready,alive,kv_used,restart_count,last_error} 是引擎状态单一真源,消掉 dict / 注解 / status 三处漂移。防双写:只有 agent 动引擎,controller 只动 desired。

5.2pod 内生命周期(model-kubelet)

Launching→ Booting→ Ready→ Draining→ Stopped ⟲backoff restart

liveness=进程存活,readiness=/health 200;boot 期路由保持 port:0(readiness gate,零 502)。退避重启封顶 60s / 上限 5 次,超限 Failed 上报换 pod。

5.2*进程模型 —— 为什么 agent 崩了数据面不断

引擎 setsid 脱离,agent 一死引擎不会被连带杀掉。但当前 warm pod entrypoint 就是 agent → agent = PID 1 → 崩 = 容器重启 = 引擎全死。故加一层极薄 init:PID 1 = tini + 重启循环,agent 崩了就地重启(不惊动 k8s);引擎(已 reparent 到 tini)照跑;agent 重启后从本地状态文件 /var/run/aibrix/engines.json(不是 etcd)re-adopt——按 pid + /health 认领活着的、只重拉真死的。类比正是 systemd → kubelet → 容器运行时。

谁崩现象收敛
engine 进程supervise 秒级发现退避重启;超限 → Failed 上报 → 换 pod
agent引擎变孤儿(但活着)init 就地重启 + re-adopt,数据面不断
controllerdesired 不更新引擎照跑,agent 本地 supervise 不断,路由冻结在最后已知态
网络分区读不到 actual保守不动路由,恢复后对账

5.3·5.4请求 hold + scale-to-zero 动态能力 · 深度降级

hold(透明唤醒,首 PR 外):撞到不可路由 claim 时有界挂住、可路由后透明转发的 UX 已在老分支验证,但 phase-1 全砍;网关保持普通 400/503 行为。

scale-to-zero(首 PR 外):redis 活跃度 + port:0 停泊 + 防抖;真机全周期已验证,含 4 个只有真集群暴露并已修复的 bug。在老分支 c7ceb886,follow-up 整捞。

5.5GPU 显存完整账本 —— 把"能 launch 很多"变成"管得住"

一张卡上 N 个引擎,显存消费者其实 5 类,现状只算了第 ② 类:

消费者谁在管现状
① 权重 Wphase-2 vLLM sleep(evict→DRAM)phase-1 无 weightSize 字段、无账
② KV(弹性)kvcachedphase-1 只观测 used/total;配额/回收移入 phase-2
③ activation + CUDA graph + 框架 overhead A没人管OOM 真凶(每引擎 ~1–3GB)
④ headroom Hkvcached (1-util)隐式预留
⑤ 碎片VMM 按页映射基本吸收

核心补法:第 ③ 类实测不预测 —— agent 在引擎 ready 后、放流量前读一次实际显存足迹(nvidia-smi/torch)记进每卡账本;KV 走 /dev/shm。每卡不变式 Σ(W+A) + Σ(KV_floor) + H ≤ HBM。v1 咨询式(算 + metric + 喂放置 + 超额告警),硬准入快速跟进。

5.6放置(选哪台机器)+ CPU DRAM 账 + 多级缓存

脊柱 = 多级缓存层级,激活/唤醒成本随 tier 递增 —— 这就是 locality cost 的物理来源:

T0HBM(active)· 权重驻留 + KV,引擎在跑最热
T1pinned CPU DRAM · phase-2 sleep L1 睡下的权重亚秒唤醒
T2node NVMe(hostPath)· 已下载权重,全 pod 共享秒级 · 真机 download 0
T3remote(HF/S3/TOS)· 冷,首次下载几十秒
◀ 便宜 / 热贵 / 冷 ▶

① 选哪台 = filter+score

Filter:候选卡查 5.5 账本能否放下(v1 咨询)。Score:权重在这台机的 tier(HBM/DRAM > NVMe > remote)+ load + DRAM 余量 → PlacementProvider。

② CPU memory 够不够

sleep L1 权重进 pinned DRAM,睡多了 DRAM 先于 HBM 爆。节点账本加 Σ(睡眠权重) ≤ DRAM 预算(读实际 free + 可配比例,非 k8s allocatable)。

③ 多级缓存谁维护

T2 缺容量上限 + LRU;DaemonSet 扫本地写节点注解喂放置;promotion/demotion 链(激活 T2/T3→T0、sleep T0→T1、压力 T1→T2)。

系统粒度 / 机制k8s 形态与我们的关系
ServerlessLLM OSDI'24分层 checkpoint 快加载 + 缩零自带集群层路线母版;其 store 在 kvcached 镜像 NO-GO

Research 机会评估intern 论文方向 —— 机制现成,"策略层"大量留白

R1SLO 感知 warm-set 管理 ★推荐MLSys/EuroSys

N 模型 M 卡、冷启动 50–120s 下,哪些保 Active/DRAM-warm/Parked 最大化 SLO?到达率预测驱动预测性 unpark;形式化为带切换成本的在线缓存问题(竞争比/regret)+ 系统实现。风险低。

R2弹性 KV 配额最优分配 ★推荐MLSys/SoCC

min/max/shares 是 HTB 启发式;共卡竞争下"给谁多少 KV"的最优解?效用最大化 + 成本不对称回收两层在线算法;对照 Prism,差异 = 显式 SLA 语义。与 R1 可拼一篇。

R3唤醒时延分解与流水线唤醒ATC/HotOS

60s 唤醒里下载/加载/compile/KV 各占多少?边加载边服务:分层快加载格式(填 sllm_store NO-GO)、CUDA C/R、compile 缓存持久化、分阶段 wake。工程外溢价值最大。

R4服务粒度谱系HotCloud/SoCC

token 级(Aegaeon)vs 空间(MuxServe)vs 模型级(我们)适用域从未被统一度量。统一成本模型 + 同 trace 三粒度实测,给"按负载选粒度"的决策图。

R5 共卡干扰与准入控制(EuroSys/ATC):kvcached 解决"放得下"没解决"跑得好";干扰画像 → 干扰感知准入,对接 placement 二期。 · 首选 R1(或 R1+R2 合体):机制现成、数据自产、故事完整,与 roadmap 直接互哺。
