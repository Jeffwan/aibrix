## A.2 External FAQ (customers)

**Q: What's actually new in v0.7.0?**
A refactored, cleanly layered batch stack (Metadata Service / planner / resource manager) and **native multi-cloud provisioning**: you can now launch batch jobs on neoclouds like **Lambda** and **RunPod**, not just your existing Kubernetes cluster — through the same OpenAI-compatible API.

**Q: How does this make batch cheaper?**
v0.7.0's lever is **sourcing**: run on the cheapest GPUs. Neocloud GPUs are typically `[50–80%]` cheaper per hour than hyperscaler on-demand. Because AIBrix's resource manager models pricing and capacity across providers, the planner can place your job where it's cheapest. (Throughput optimizations, idle-fleet harvesting, and spot/cross-region cost arbitrage build on this foundation in later releases.)

**Q: How is this different from SkyPilot?**
SkyPilot is a workload-agnostic CLI that launches arbitrary jobs on many clouds. AIBrix is a **cloud-native (Kubernetes), inference-native, API-first entry point for batch**: it speaks OpenAI Batch end-to-end, understands your inference data plane (KV cache, prefix reuse, prefill/decode), and **provisions neoclouds natively — no SkyPilot underneath.** If you want a front door for *batch inference* rather than a generic job launcher, that's AIBrix. We compete with SkyPilot here; we don't sit on top of it.

**Q: Which clouds / neoclouds are supported in v0.7.0?**
Kubernetes (your existing cluster) plus native **Lambda** and **RunPod** backends to start, designed to extend to more providers. We're prioritizing inference-nativeness over raw cloud count.

**Q: Is it still OpenAI-Batch compatible? Do I have to change my code?**
Yes, and no. Same `/v1/files` + `/v1/batches`, same JSONL, 24-hour window. Migrating is a `base_url` change. You choose the provider/profile; the API is unchanged.

**Q: Where does my data go?**
Into the provider you choose, inside your accounts and your object store (S3/TOS/GCS). Self-hosted means your compliance boundary — not a third party's black box.

**Q: What about all the "elastic / harvesting / cheaper-than-50%" ideas?**
Those are the roadmap (see "What's next"). v0.7.0 deliberately lands the **foundation** — a cloud-native, multi-provider batch entry point — first. The advanced cost levers ride on top of it.

## A.3 Internal FAQ (stakeholders)

**Q: Why is "refactor + neocloud" the right v0.7.0, instead of shipping a flashy batch feature?**
Three reasons. (1) The refactor is *already underway* (`#2239` planner provider-split, `#2245` RM extension support, `#2243` upstreamable batch components) — v0.7.0 finishes a coherent layer. (2) Neocloud sourcing is a **low-risk, immediate** cost story that needs zero scheduling cleverness. (3) It's the **substrate** every later lever (spot, cross-region, harvesting) depends on. Shipping a fragile harvesting feature first would risk online SLOs and bury the clean "cloud-native batch entry point" narrative.

**Q: We said we compete with SkyPilot. Are we reinventing it?**
We're building the *inference-native, cloud-native, API-first* slice — not a general cross-cloud launcher. We own native provisioners for the key neoclouds so we control provisioning + placement + API + data plane end-to-end. Ceding provisioning to SkyPilot would cede the entry point and the cost-optimization brain to a competitor. Honest boundary: SkyPilot supports more clouds today; we lead on inference-nativeness, K8s-nativeness, the OpenAI-Batch surface, and control-plane integration, and we expand provider coverage over time.

**Q: What's the colocation/harvesting story, and why isn't it in v0.7.0?**
It's deferred because it touches paying-customer online SLOs and the papers all assume single-model/single-engine. Our near-term *research* bet (parallel to v0.7.0) is the prerequisite: an **online↔offline isolation guarantee** — a mechanism with a *bounded, demonstrable* online-latency impact (Valve/ConServe lineage), validated by the W5 trace experiment. Harvesting becomes a feature only once that guarantee holds (P4, single-model first).

**Q: What's the biggest risk in v0.7.0 itself?**
Provider integration surface (auth, instance lifecycle, failure modes, egress/pricing accuracy) across heterogeneous neocloud APIs, and keeping the refactor from regressing the existing OpenAI-compatible behavior. Mitigation: start with two providers (Lambda, RunPod), strong contract tests on the catalog/provisioner/planner-backend interfaces, and keep Kubernetes as the default path.

**Q: What does success look like 90 days post-launch?**
Batch jobs launching on Lambda and RunPod from the OpenAI-compatible API in real deployments; a published `$/1M tokens` comparison showing neocloud sourcing materially under hyperscaler on-demand (and under closed Batch APIs where applicable); the cost calculator updated with measured neocloud numbers; and a crisp "AIBrix vs SkyPilot for batch" positioning page.

**Q: What are we explicitly NOT doing in v0.7.0?**
Harvesting/colocation, prefix-reorder throughput, spot/cross-region arbitrage, CPU/attention offload, workflow batch, and any "10×" marketing. Roadmap, not launch.

## AIBrix Batch v0.7.0: A Cloud-Native Entry Point for Batch Inference on Any Cloud

AIBrix is a composable, cloud-native LLM inference infrastructure designed to deliver high performance and low cost at scale. With v0.7.0, we're making AIBrix the **cloud-native entry point for batch inference** — and the cheapest path to a batch token starts with where you run it.

### Why we built this

Batch inference today forces a bad choice. A closed Batch API gives you a flat 50%-of-list discount on a black box you can't see into, tune, or run on your own hardware. A workload-agnostic launcher like SkyPilot can put a job on many clouds, but it doesn't know what an inference engine is — you wire up the model, the routing, the KV cache yourself. And a dedicated cluster pins you to one expensive hyperscaler.

We think batch deserves a proper **cloud-native, inference-aware front door**: one OpenAI-compatible API, running on Kubernetes, that can place your job on the cheapest GPUs available — including neoclouds — and that understands the inference data plane underneath. That's what v0.7.0 builds.

### What's new in v0.7.0

**1. A cleanly layered, refactored batch stack.**
We split batch into three composable layers with stable interfaces: the **Metadata Service** (the OpenAI-compatible API and job lifecycle), the **planner** (placement and scheduling), and the **resource manager** (resource discovery, pricing, and provisioning). This refactor (building on `#2239`, `#2243`, `#2245`) is what makes everything below — and the roadmap above it — possible.

**2. Native neocloud provisioning — launch on Lambda and RunPod.**
AIBrix's resource manager is now multi-provider. You can launch batch jobs on **Lambda** and **RunPod** directly — no SkyPilot, no separate orchestrator — alongside your existing Kubernetes clusters. Neocloud GPUs are routinely `[50–80%]` cheaper per hour than hyperscaler on-demand, so for latency-tolerant batch work, the simplest cost win is to run it somewhere cheaper. *(Figure: $/1M tokens on neocloud vs hyperscaler on-demand vs closed Batch API.)*

**3. Pricing- and capacity-aware placement (foundation).**
The resource manager models regions, instance types, and **pricing/availability predictions** per provider; the planner uses them to place a job on capacity that fits both the job and your budget. This is the foundation the cost roadmap (spot, cross-region) builds on.

**4. Cloud-native and inference-native, end to end.**
It runs on Kubernetes, integrates with the AIBrix control plane (routing, KV cache, P/D disaggregation), and stays OpenAI-Batch compatible. Migrating from a closed Batch API is a `base_url` change.

### How it works (architecture)

*(Diagram: OpenAI-compatible API → Metadata Service → planner (placement, pricing/capacity-aware) → resource manager {Kubernetes | Lambda | RunPod | …} → AIBrix inference data plane → results to object store.)*

The three seams that make providers pluggable:
- **`catalog`** — per-provider resource discovery + pricing/predictions.
- **`provisioner`** — per-provider instance launch/lifecycle.
- **planner backend** — per-provider placement decisions (the hook for future cost/capacity-aware scheduling).

SkyPilot launches any job anywhere. AIBrix Batch is the front door for *batch inference* — it speaks OpenAI Batch, knows your KV cache, and provisions the cheapest GPUs itself.

### What's next

v0.7.0 is the foundation. On top of it, the roadmap makes AIBrix the lowest-cost place to run batch inference on infrastructure you control:

- **Online↔offline isolation guarantee** — our key research bet: a mechanism with a *bounded, demonstrable* impact on online latency, so spare online-fleet capacity can later be harvested for batch *safely*.
- **Cost-aware spot & cross-region/provider placement** — extend the pricing-aware planner with spot and an inference-native checkpoint/restore (request-queue + prefix-KV granularity, seconds not minutes), bringing the Sky Computing cost model to inference — natively.
- **Batch-aware throughput** — whole-job prefix reuse and compute/memory blending for more tokens per GPU-hour.
- **Workflow batch** — submit a batch of multi-step agentic workflows as one optimized job.
